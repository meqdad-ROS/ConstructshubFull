# ConstructsHub — AI evaluation harness (D1)

Repeatable scoring for the three AI capabilities the SRS gates on:

| Track | What it measures | Metric |
| --- | --- | --- |
| **detection** | Image search / construction-material object recognition (§6.3) | per-class precision, recall, F1 + image-level accuracy |
| **ocr** | Document & handwritten-Arabic OCR (§6.3, §9.4) | CER, WER |
| **bim** | IFC quantity extraction (§6.5) | mean quantity error % + line coverage |

This harness is the **acceptance gate** for tasks D2–D5. No AI feature is
accepted on the agent's word alone — the agent must run this harness against
the shipped service and publish the generated report.

## Install

Nothing to install. The runner is stdlib-only — Python 3.11+.

Pillow (`pip install Pillow`) is required ONLY to regenerate the sample
datasets with `build_datasets.py`. The harness itself does not depend on
Pillow or any other third-party package; the samples ship pre-generated under
`datasets/*/samples/`.

## Run

```bash
# Full baseline (all 50+ detection, 30+ OCR, 5 BIM samples). Writes a
# timestamped report under ai/evals/reports/.
python -m ai.evals.runner

# One track:
python -m ai.evals.runner --track ocr
python -m ai.evals.runner --track detection --iou 0.5 --score-threshold 0.0
python -m ai.evals.runner --track bim --bim-tolerance 5.0

# The 10-sample smoke subset CI uses (same as `.github/workflows/ai-evals.yml`):
python -m ai.evals.runner --smoke --out ai/evals/reports/ci-smoke.md

# Point it at a live OCR endpoint (eg Next.js dev server):
OCR_ENDPOINT=http://127.0.0.1:3000/api/search/ocr python -m ai.evals.runner --track ocr

# Point it at the live BIM service (needs the HMAC token):
BIM_ENDPOINT=http://127.0.0.1:8081/parse \
  BIM_SERVICE_TOKEN="$(cat .env | grep BIM_SERVICE_TOKEN | cut -d= -f2)" \
  python -m ai.evals.runner --track bim
```

## Dataset layout + provenance

Each dataset is one directory with a `manifest.json` describing every sample's
origin, licence, language, included-vs-staged status, and ground truth. The
loader records a sha256 of each sample at run time so the report pins the
exact bytes evaluated.

```
ai/evals/datasets/
  detection/
    manifest.json
    samples/*.png
  ocr/
    manifest.json
    samples/*.png
  bim/
    manifest.json
    samples/*.ifc
ai/evals/ci/
  smoke-detection.json   # first 10 included samples
  smoke-ocr.json
  smoke-bim.json
```

**Synthetic placards & rendered print are honest ground truth**: we drew the
rectangle at coordinates `(x,y,w,h)`, we rendered the exact transcript into
the image. There is no gold-annotation guessing. The report labels these
"synthetic" so a reader cannot confuse them with photographs of real sites.

**The staged-acquisition entries are visible gaps**. Each has
`"included": false` and a `provenance.source` of `pending`. The loader skips
them with reason so the report shows them in a "pending" column rather than
pretending they are covered. Below is the explicit curator plan.

## Reading a report

Every report opens with the git revision + harness version + UTC timestamp.
Each track section lists the dataset name/version, the service name (eg
`waquor-next`, `tesseract-cli`, `offline-zero`, `local-step`), the metric
table, and a per-sample / per-line body. "Service unavailable" is reported
explicitly — a missing OCR server does NOT turn into a 100% match claim.

The caveats at the bottom document the limitations plainly. The detection
section is currently scored against the OCR-word-box baseline described in
`waquor/lib/search/image.ts`; the report labels this as `detectorKind:
ocr-words` so no one mistakes it for a trained detector. Replacing it with a
real detector in D2 does not change the report format — just the service
name and the scores.

## Interpreting metric policies

* **Detection.** Greedy IoU match, highest-score prediction first. A label
  swap (predict `rebar`, truth is `steel-beam`, boxes overlap > IoU) counts
  as **two mistakes** — a FP for the predicted class and a FN for the truth
  class. Image-level accuracy counts an image as "correct" only when every
  prediction matches a truth without mislabel and no truth is missing.
* **OCR.** Both prediction and truth pass through the same normaliser
  (NFKC, Arabic-Indic → ASCII digits, tashkeel stripped, whitespace collapsed,
  Latin lowercased). You will see "٥٠mm" and "50mm" score as identical. An
  empty-truth sample is excluded from the mean but counted as "truth empty"
  so a reader sees it.
* **BIM.** Match predictions to truth by `(ifc_class, unit)` (case folded).
  A missed truth line is 100% error; an extra predicted line is 100% error.
  A truth of 0 (zero-truth) is reported as either 0 (prediction also 0) or
  infinity — the mean honours those lines explicitly.

## Approving new metrics / new thresholds

The CI gate (`.github/workflows/ai-evals.yml`) fails hard on crashes,
malformed output, or dataset problems. **Thresholds** that gate a feature
(eg "detector must beat F1 > 0.6 to merge D2") belong in a service-side
regression test, not in this harness — the harness scores what the service
emits; the service's acceptance test asserts the score. If a run comes back
with "we had to lower the threshold to pass", that is a reason to open an
investigation, not a reason to commit a lower threshold.

## No new packages

The runner, metrics and services use `urllib`, `hashlib`, `hmac`, `json`,
`subprocess`, and `pathlib` — all stdlib. Pillow is required only to
regenerate the sample datasets (`build_datasets.py`), not to run the harness;
regenerated samples are then committed. Adding a dependency to this harness
requires explicit approval and a `requirements.txt` entry.
